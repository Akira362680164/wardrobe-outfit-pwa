# Wardora 合规官网设计规格

## 1. 目标

在现有 Next.js 工程内建设 Wardora 官方网站，用于公开展示产品用途、隐私政策、用户协议、账号注销说明、联系方式、ICP备案信息和公安联网备案状态。官网不提供交易、公众信息发布、论坛、金融、医疗、新闻或教育培训等需专项许可的服务。

本次只建设可公开部署的基础合规页面，不提交备案申请，不修改生产 DNS，不伪造主体、联系方式或备案编号，也不改变 `api.zhengfangapps.cloud` 的现有 API 行为。

## 2. 已确认的现状

- 当前根路由 `/` 渲染 `AppRoot`，也是 Capacitor Android 静态导出的入口。
- Next.js 使用 App Router、静态导出 `output: "export"` 和 `trailingSlash: true`。
- Android 的 `webDir` 为 `out`，默认 `npm run build` 产物会进入 APK 同步链路。
- 当前公开法律页面只有 `/legal/privacy` 和 `/legal/terms`，内容服务于 App 内认证流程。
- 当前代码未发现 App 内账号注销入口。
- 仓库未发现可公开使用的运营主体名称、联系邮箱、ICP 备案号或公安备案号。
- 生产部署仅包含 PostgreSQL、wardrobe API 和 `api.zhengfangapps.cloud` 的 Caddy 反向代理，尚无官网静态托管配置。
- 已确认运行时外部服务包括 MiniMax AI、腾讯云 SES，以及微信登录相关接口；Capacitor Camera、Filesystem、App、Keep Awake 等属于 App 原生能力。上线前仍须由运营方复核实际 SDK 和数据处理清单。

## 3. 架构决策

### 3.1 同一工程、双构建目标

采用构建时目标切换，不在运行时根据浏览器或 Capacitor 环境猜测页面：

- 默认 App 构建继续执行 `npm run build`，根路由仍为 `AppRoot`，输出到 `out`。
- 官网构建执行 `npm run build:website`，根路由渲染 Wardora 官网，输出到独立的 `out-website`。
- 官网构建不能覆盖或污染 Android 使用的 `out`；构建脚本负责以受控方式准备独立产物。
- 两种构建复用现有 Next.js、React、Tailwind、Lucide、全局设计 Token、类型系统和测试工具，不新建第二个前端工程，不引入新依赖。

构建目标由服务端可读取的环境变量决定，并在类型安全的辅助模块中收敛。生产页面不得依赖客户端首次执行后再切换，否则会损害 SEO、无脚本可读性和首屏稳定性。

### 3.2 路由

官网构建必须公开生成：

- `/`：Wardora 首页。
- `/privacy`：隐私政策。
- `/terms`：用户协议。
- `/account-deletion`：账号注销说明。
- `/contact`：联系我们。
- 未知路径：自定义 404 页面。
- `/robots.txt` 与 `/sitemap.xml`：官网抓取和索引入口。

App 现有 `/legal/privacy`、`/legal/terms` 保留，避免破坏注册、登录和协议查看流程。公开法律页与 App 法律页从同一份结构化内容源读取，展示外壳可以不同，但事实和更新时间不得漂移。

### 3.3 文件边界

计划采用以下职责划分：

- `src/lib/site-config.ts`：统一、类型安全的公开站点配置及缺失值状态。
- `src/lib/site-build-target.ts`：构建目标判断，不包含页面文案。
- `src/content/legal-content.tsx`：隐私政策、用户协议和账号注销的共享结构化内容。
- `src/components/site/*`：官网 Header、Footer、移动菜单、法律文档布局和首页区块。
- `src/app/*`：负责共享路由实现、metadata 和页面组合；根目录 `app/*` 是当前 Next.js 实际识别的 App Router，通过薄转发文件接入共享实现。
- `src/components/build-home.tsx` 与官网构建别名：保证默认构建只加载 `AppRoot`，官网构建只加载官网首页，避免把完整 App JavaScript 打进官网。
- `scripts/build-website.mjs`：官网独立静态构建产物管理。
- `scripts/test-wardora-compliance-site.ts`：静态合同与敏感信息边界检查。
- `docs/deployment/wardora-website.md`：基于现有 Caddy 架构的部署手册。

每个文件只承担一种职责；不把整站继续堆入 `wardrobe-app.tsx`，也不修改服务端业务接口。

## 4. 统一站点配置

统一配置包含：

- `siteName`
- `siteDescription`
- `domain`
- `contactEmail`
- `operatorName`
- `icpNumber`
- `policeRecordNumber`
- `policeRecordUrl`
- `privacyUpdatedAt`
- `termsUpdatedAt`

公开且稳定的默认值可写入配置；需由运营方提供的值通过明确命名的构建环境变量注入。缺失时遵守以下规则：

- 不显示 `undefined`、空字符串、空链接或虚构编号。
- ICP 缺失时显示“ICP备案信息上线前待配置”，不链接到工信部备案查询页。
- 公安备案号缺失时显示“公安备案信息办理中”。
- 联系邮箱缺失时显示“公开联系邮箱上线前待配置”，不生成 `mailto:`。
- 主体名称缺失时显示“运营主体上线前待确认”，不伪装成公司名称。
- 公安备案号和链接必须同时有效才生成链接。
- 生产官网构建可以在公安备案尚未完成时成功，但构建日志应提示待补配置。

ICP备案号取得后链接至工信部备案查询网站；公安备案号取得后使用配置中的真实查询链接。敏感信息、密钥、数据库配置和内部地址不进入该配置。

## 5. 页面与内容设计

### 5.1 全局导航与页脚

桌面导航包含 Wardora、首页、隐私政策、用户协议、账号注销、联系我们。移动端使用按钮控制的折叠菜单，具备 `aria-expanded`、明确焦点样式、44px 以上触控区域，并在选择链接后关闭。

页脚包含 `© 2026 Wardora`、四个合规入口、真实配置状态下的备案信息。页脚不能截断备案号，也不能生成空链接。

### 5.2 首页

首屏使用任务书规定的标题、副标题、说明和两个按钮。页面不展示应用商店下载按钮。

视觉概念为“编辑式衣橱档案”：文字区旁使用纯 HTML/CSS 的静态衣物分类、穿搭组合和日期计划卡片表达产品范围，不使用虚构应用截图、用户数据、自动轮播或视频。

核心功能展示六项：衣物管理、穿搭管理、穿搭计划、购物意向、AI 辅助识别、云端同步。首页必须以独立、清晰的区块显示服务边界：Wardora 不提供电商交易、公众内容发布、社交论坛、金融服务或其他需专项行政许可的服务。

### 5.3 隐私政策

隐私政策覆盖任务书规定的 15 个章节，并如实描述：

- 邮箱、选填手机号登录名、验证状态和登录凭证处理。
- 衣物图片、衣物字段、套装、穿搭计划、购物意向及用户主动填写的信息。
- 服务器是正式衣橱数据和图片的权威来源。
- 图片可能上传至 Wardora 服务器用于存储和同步；用户主动触发 AI 时，相关图片和请求会用于 MiniMax 识别。
- MiniMax 结果只作辅助，由用户最终确认。
- Android 认证凭据使用安全存储；MiniMax Key 当前保存在本机 localStorage，并在主动调用时临时经 API 转发，服务器不保存该 Key。
- 必要设备、日志、错误和脱敏诊断数据的处理边界；远程诊断只能由用户主动提交。
- 腾讯云 SES 用于验证码邮件；微信接口用于小程序登录或手机号能力；Capacitor 原生插件用于 App 设备能力。
- Cookie、sessionStorage、localStorage、Service Worker 和页面内存状态的实际用途，避免宣称“完全不收集数据”或“所有数据仅保存在本地”。

实际数据保存期限、运营主体和完整第三方 SDK 清单无法仅由仓库完全确认，页面和交付清单必须要求上线前复核，不擅自承诺期限。

### 5.4 用户协议

用户协议覆盖规定的 15 个章节，明确服务范围、账号责任、上传图片合法使用权、违法或侵权内容限制、AI 误差、用户核对责任、服务可用性边界、合理责任限制、未成年人使用和法律适用。协议不得承诺永久免费、永久可用，也不得虚构公司主体或使用明显不合理的免责条款。

### 5.5 账号注销说明

由于当前代码未发现 App 内注销入口，页面不得写“Wardora → 设置 → 账号与安全 → 注销账号”。页面说明用户当前可通过公开联系邮箱提交申请；邮箱尚未配置时明确提示上线前必须补齐有效渠道。

页面说明注销可能删除账号资料、衣物数据与图片、穿搭组合、穿搭计划、购物意向及其他账号关联个人数据；依法需要保留的信息按适用法律处理。页面不承诺代码尚未实现的固定处理时限，只说明将在核验身份和申请范围后依法处理。

“补充 App 内注销入口”列为高优先级合规待办。

### 5.6 联系我们

显示产品名称、服务类型、统一联系渠道状态和问题类型：账号、数据、隐私、注销、安全、其他反馈。不展示私人手机号、家庭住址、内部服务器信息或后台地址。

### 5.7 404

404 页面使用简短说明、返回首页按钮和合规页面入口。静态托管配置必须让未知路径进入自定义 404，同时不把 API 请求导向官网。

## 6. 视觉规范

- 复用现有 `ink/paper/mist/surface/denim/moss/clay` Token 和 `appAmbient` 背景。
- 最大内容宽度 1120px，法律正文约 760px，移动端左右边距 20px。
- 导航高度约 68px；普通控件圆角 10px 至 12px，官网内容卡片圆角 16px，避免另建与 App 冲突的视觉系统。
- 背景为白色到暖灰的低饱和层次，卡片使用浅描边和克制阴影；不使用高饱和蓝、复杂渐变、视频背景、自动轮播或过度动画。
- 正文行高不低于 1.7，法律文本保持稳定阅读宽度和足够对比度。
- 只使用轻量 CSS 进入效果或 hover/focus 反馈，并完整支持 `prefers-reduced-motion`。
- 官网不加载外部字体、追踪脚本或第三方图片，避免额外隐私和性能风险。

## 7. SEO 与无障碍

- 官网构建使用 Wardora 标题模板、描述、metadata base、canonical URL 和基础 Open Graph 信息。
- 提供 favicon、manifest、robots 和 sitemap；sitemap 只包含公开官网页面。
- 页面采用 `header`、`nav`、`main`、`section`、`article`、`footer` 等语义标签，标题层级连续。
- 导航、菜单按钮和图标按钮具备可访问名称；当前页面使用 `aria-current="page"`。
- 键盘焦点清晰；颜色不是唯一状态信号；触控区域不小于 44px。
- 375、390、430、768、1024、1440px 均不得出现横向滚动、导航溢出、备案号截断或过小字号。

## 8. 错误与缺失配置处理

官网没有数据库请求和业务 API 请求，因此不存在页面级数据加载错误。错误处理集中在配置和静态托管：

- 无效邮箱、域名或备案链接不会生成可点击链接。
- 缺失运营信息显示诚实、可识别的待配置状态。
- 未知路径返回自定义 404。
- 构建脚本失败时保留默认 App 构建目录，不用永久删除命令清理工作区。
- 官网部署故障不能影响 `api.zhengfangapps.cloud` 的 API 反向代理。

## 9. 测试与验收

### 9.1 自动化

- 官网合同测试检查六个公开页面、规定文案和章节、统一配置、备案占位规则、无空链接、robots、sitemap、canonical 和 404。
- 构建目标测试确认默认根路由仍加载 `AppRoot`，官网目标根路由加载官网。
- 执行 `npm run lint`；若仓库脚本因 Next.js 15 不再提供 `next lint` 而失败，如实记录，不伪造通过。
- 执行 `npm run typecheck`、`npm test`、`npm run build` 和 `npm run build:website`。
- 执行现有受影响测试，确认 App 法律页和认证协议入口不回归。

### 9.2 浏览器与静态产物验证

使用本地静态服务器和 Playwright 验证：

- 首页、隐私政策、用户协议、账号注销、联系页可直接访问并刷新。
- 未知路径显示 404。
- 移动菜单可打开、关闭和导航。
- 页脚链接全部有效，无空 `href`。
- 六个目标宽度无横向滚动、遮挡或截断。
- 控制台无明显错误，HTTPS 部署配置不引入混合内容。
- 官网产物不包含密钥、数据库名称、内部路径、管理地址、内部 IP 或端口。

### 9.3 App 与 API 回归边界

- 默认 `npm run build` 仍生成 App 根入口并输出 `out`。
- `npm run build:website` 只生成官网独立产物，不覆盖 Android `webDir`。
- 不修改服务端路由、API Caddy 站点块或微信小程序代码。
- 本次官网产物不进入 APK，因此不递增 App 版本、不构建 APK；若实现过程实际改变默认 App 产物或 Android 资源，则必须重新评估版本和 Android 验证要求。

## 10. 部署设计

推荐使用 `https://zhengfangapps.cloud` 作为唯一 canonical，`https://www.zhengfangapps.cloud` 永久跳转至根域名：

- 根域名 DNS 指向承载官网静态文件的服务器或托管平台。
- `www` 使用 CNAME 或等效记录指向根域名入口，再由 HTTPS 层跳转。
- Caddy 为根域名签发 HTTPS 证书、启用 HTTP 到 HTTPS 跳转并托管 `out-website`。
- `api.zhengfangapps.cloud` 保持现有独立站点块和 `reverse_proxy 127.0.0.1:3000`，不得合并进官网静态路由。
- 发布前配置公开站点环境变量，执行官网构建，将产物同步至独立发布目录，验证配置后再 reload Caddy。
- 部署文档提供 DNS、证书、Caddy、环境变量、构建、发布、回滚和 `curl` 验证命令；本次不直接操作生产 DNS 或服务器。

## 11. 合规待办

上线前至少完成或确认：

1. 运营主体名称和公开联系邮箱。
2. 真实 ICP 备案号及展示链接。
3. 网站公安联网备案及备案号链接。
4. Android App 工信部备案和公安联网备案。
5. 微信小程序备案和公安联网备案。
6. App 和小程序内备案信息展示。
7. 隐私政策与实际 SDK、服务商、数据期限、存储地点的一致性。
8. App 内账号注销入口。
9. 用户数据导出和删除能力。
10. 法律文本由用户或专业法律顾问复核。

- 不提交主工作区既有未跟踪文件、环境文件、生成目录或敏感信息。
- `VERSION_HISTORY.md` 记录实际改动、验证结果和未验证风险。
